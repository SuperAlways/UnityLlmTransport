# 03 · pi 通讯需求矩阵

> **目的**：把 `pi-ai` / `pi-agent-core` 在“通讯层”的需求逐项拆出来，明确哪些属于 **UnityLlmTransport**，哪些属于 **PiUnityAgent.Ai**。
> **上游版本**：pi（原版）`v1.5.0` / `f9a263655`。
> **参考**：pi.net `main` / `2d6757b`（只作 C# 语言映射参考，net9/10，不作为运行时基线）。
> **日期**：2026-11-06

---

## 1. 分层口径

```
Provider adapters（协议 JSON 映射）
  OpenAI Chat/Responses、Anthropic、Gemini、Bedrock、Mistral…
        │  依赖
        ▼
UnityLlmTransport（本组件）
  HTTP/SSE/chunked/NDJSON/WebSocket、认证钩子、代理/TLS、超时、取消、主线程
        │
        ▼
Unity 宿主（Mono/IL2CPP、主线程、生命周期）
```

- **传输层**：只负责“字节怎么出去、怎么回来、怎么中止、怎么送到主线程”。
- **协议层**（PiUnityAgent.Ai）：负责 JSON 结构、SSE 事件语义、tool_calls/usage/stopReason。
- **认证层**：API Key/OAuth/SigV4/ADC 的取得与刷新；传输层只提供“应用凭据/签名”的钩子。

## 2. pi 的通讯面总览

### 2.1 API / Provider 家族

| 家族 | pi 文件 | 传输形态 |
|---|---|---|
| OpenAI Chat Completions | `api/openai-completions.ts` | HTTP + SSE |
| OpenAI Responses | `api/openai-responses.ts`、`openai-responses-shared.ts` | HTTP + SSE |
| Azure OpenAI Responses | `api/azure-openai-responses.ts` | HTTP + SSE |
| OpenAI Codex Responses | `api/openai-codex-responses.ts` | **HTTP + SSE 或 WebSocket** |
| Anthropic Messages | `api/anthropic-messages.ts` | HTTP + SSE |
| Google Gemini / Vertex | `api/google-generative-ai.ts`、`google-vertex.ts` | HTTP + SSE |
| Bedrock Converse | `api/bedrock-converse-stream.ts` | HTTP + SSE（SigV4） |
| Mistral Conversations | `api/mistral-conversations.ts` | HTTP + SSE |
| Cloudflare Workers AI | `api/cloudflare-workers-ai-system-one.ts` | HTTP |
| OpenAI-compatible 本地/代理 | `api/openai-completions.ts` + compat | HTTP + SSE（部分 NDJSON） |
| 图片 | `api/openrouter-images.ts` 等 | HTTP |
| 分类 | `api/llama-cpp-classify.ts`、`openai-decisions.ts`、`system-one` | HTTP |

> 结论：**不只是 SSE**。传输层至少要覆盖 HTTP、SSE、chunked、WebSocket；NDJSON 作为兼容端点选项。

### 2.2 传输相关选项（`ProviderRequestOptions` / `StreamOptions`）

| 选项 | pi 含义 | 传输层职责 |
|---|---|---|
| `signal` | 取消 | 取消传播 + 中止底层连接 |
| `fetch` | 自定义 fetch 实现 | 传输实现可注入 |
| `headers` | 自定义 headers；`null` 抑制默认头 | 合并/覆盖 |
| `identity` | UA / provider 归属头 | 注入 |
| `env` | provider 作用域环境变量 | 传给实现（代理/区域等） |
| `onPayload` | 发送前改写请求体 | 发送前钩子 |
| `onResponse` | 收到响应头后回调 | 响应头钩子 |
| `onProviderStreamEvent` | 原始流事件观察 | 解析前钩子 |
| `timeoutMs` | 请求超时 | 连接/首字节/空闲策略 |
| `maxRetries` | 客户端重试次数 | 重试策略（或交给上层） |
| `maxRetryDelayMs` | 重试等待上限 | 退避上限 |
| `transport` | `sse/websocket/websocket-cached/auto` | 多传输选择 |
| `websocketConnectTimeoutMs` | WebSocket 握手超时 | 单独超时 |
| `cacheRetention` / `sessionId` | 提示缓存 | header/会话字段 |
| `telemetry` | 追踪 span | 透传/观察 |

### 2.3 认证与签名

| 能力 | pi 形状 | 传输层职责 |
|---|---|---|
| API Key | `ApiKeyAuth` / `Credential` | 注入 header；不负责存储 |
| OAuth | `OAuthAuth`、login/refresh/logout、`AuthInteraction` | 注入/刷新后的 token；不负责交互 UI |
| AWS SigV4 | Bedrock adapter 内部 | 提供请求签名钩子（发送前） |
| GCP ADC / Service Account | Google adapter 内部 | 提供 token 获取/注入钩子 |
| Azure AD | Azure adapter | 注入 bearer token |
| 凭据存储 | `CredentialStore` | 不负责；认证层实现 |

### 2.4 长任务与多模态

| 能力 | pi 形状 | 传输层职责 |
|---|---|---|
| Deferred | `DeferredHandle`、`fetchDeferred`、`cancelDeferred` | 支持长轮询/再次请求/取消；handle 语义在协议层 |
| 图片 | `generateImages` / `AssistantImages` | HTTP 请求/响应；多模态编码在协议层 |
| 分类 | `classify` / `ClassifierResult` | HTTP 请求/响应；结构化解析在协议层 |
| 模型目录刷新 | `refreshModels` / `Models.refresh` | HTTP + 认证；目录合并/持久化在目录层 |

### 2.5 错误与重试

- `provider-retry.ts`：可重试状态 `408/409/429/5xx`、网络错误；尊重 `x-should-retry`、`Retry-After`、`retry-after-ms`；指数退避 + 抖动。
- `error-body.ts`：把 HTML/JSON 错误体归一化成可读文本。
- 传输层应提供：状态码、响应头、错误体读取、错误分类；**是否重试由上层决定**。
- 流中途失败不重试（避免重复内容/重复计费）。

## 4. 责任边界结论

### 传输层（UnityLlmTransport）

- 通用 HTTP/SSE/WebSocket 字节管道；
- 认证/签名/代理/TLS/超时的**注入点**；
- 取消 = 中止底层连接；
- 错误分类所需的状态码/headers/错误体；
- 主线程交付与生命周期；
- 可 mock、可录制。

### 协议层（PiUnityAgent.Ai）

- 请求 JSON 结构、模型参数、compat；
- SSE 事件解析、`[DONE]`、delta 聚合；
- tool_calls 按 index 拼接、usage、stopReason；
- provider 特定错误文本归一化；
- Deferred handle 语义、图片/分类结果解析。

### 认证层（可独立）

- API Key/OAuth 登录、刷新、凭据存储；
- SigV4/ADC/Azure AD 签名；
- 传输层只消费“应用后的凭据/签名结果”。

## 5. UnityLlmTransport 的最小能力集

### P0（MVP）

- T1 HTTP、T2 SSE 字节流、T3 chunked；
- T9 headers、T10 传输注入、T15 分层超时、T16 取消；
- T18 回调钩子（至少 onResponse）；
- T19 错误体读取；
- 主线程交付、可 mock。

### P1

- T6 API Key、T7 OAuth 注入、T11/T12 代理/TLS 选项；
- T17 重试分类；
- T20 Deferred；
- T22 目录刷新所需通用能力。

### P2

- T5 WebSocket；
- T13 HTTP/2（桌面 HttpClient）；
- T24 Telemetry；
- WebGL/NDJSON 兼容。

---

## 6. 关键结论

1. pi 的通讯面**远宽于 OpenAI SSE**：至少包含 HTTP、SSE、chunked、WebSocket、多种认证、Deferred、图片/分类、目录刷新。
2. 传输层**只吐字节**；SSE/toolcall/usage 解析属于协议层；否则 UnityLlmTransport 会绑死 provider。
3. 认证/签名是**钩子**，不是传输实现；否则无法同时支持 ApiKey/OAuth/SigV4/ADC。
4. 超时必须是**分层看门狗**；不能依赖 `UnityWebRequest.timeout`。
5. 取消必须**中止连接**，不是停止读取。
6. 传输必须可替换；UWR/HttpClient/RawTcp/WebSocket 只是实现，不是接口。
